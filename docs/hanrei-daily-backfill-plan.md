# 判例の要約・リンク解析・Wiki化を毎日進める計画

作成日: 2026-10-25（日本時間）。本書は実装計画であり、以下の過去分の自動投入はまだ有効化していない。

## 目標と開始時の設定

既存の `Update LLM wiki`（毎日09:00 JST）で、新規判例に加えて過去判例も継続して要約する。まずは新規最大3件・過去最大2件、合計最大5件/日とする。過去枠は新規が多い日にも確保し、失敗分の再試行も各枠の件数に含める。件数は「必ず完成する数」ではなくLLMに渡す上限とし、翌日への失敗分の持ち越しで上限を超えない。

過去2件/日なら30日で最大60件。初週は14件を上限に、引用、説明、処理時間、公開反映を確認する。その後も自動では増量せず、運用設定から過去5〜10件/日へ変更できるようにする。開始・停止・件数変更にコード修正を必要としない。

現在の索引は44,980件、試験作成済みは10件。残りを2件/日で全件処理すると約62年かかるため、当面の成果は全件網羅率に加え、対象分野の充実度で測る。行政・労務・生活保護から役に立つまとまりを作り、品質と費用を見て速度を調整する。

## 現状で再利用する処理

- `wiki-plan` は初回の索引を基準として記録し、その後に初めて現れた事件IDを処理する。既存の新規検知基準は維持する。
- `wiki-queue-hanrei` は過去の事件IDを最大10件、手動で投入できる。今回作成した10件は完了済みとして引き継ぐ。
- `update-corpus-data.yml` の `hanrei-fetch-bodies --limit 200` は、本文未取得の既存キャッシュへPDF抽出本文を段階的に追加し、R2へ保存する。Wiki生成のために同じPDF収集バッチを新設しない。
- 7節のLLM解説、裁判所の判示事項・裁判要旨の原文表示、資料の固定、引用検査、法令への逆リンク、同じ法令・条番号による関連判例、公開用JSON・グラフの出力は既存処理を使う。

## 1. 過去分の選択と処理状態

新規・過去・手動指定を区別する。既存の `.lawpub/hanrei-intake.json` に後方互換のある取り込み種別を加え、過去候補の巡回位置・再試行予定・選択理由もWikiブランチに保存する。既存のpendingは新規扱いとし、初回基準の `seen` を「要約済み」と解釈しない。

候補は配信済みの判例索引を基準に選ぶ。行政事件訴訟法・労働基準法・生活保護法などの既存 `links/law-to-hanrei/{law_id}.json` を使い、まず次の順で優先する。

1. 指定分野で、既存Wikiと同じ条文を扱う未処理判例。
2. 指定分野のほかの未処理判例。
3. 全体の未処理判例。

最初の過去枠2件は、指定分野の優先枠1件と、全体を巡回する枠1件に分ける。片方に候補がなければもう片方へ回す。分野内では裁判日を和暦から正規化して新しい順、同日なら事件IDで安定して並べる。日付不明も除外せず巡回対象にする。全体枠は永続化した巡回位置から進め、一部の分野や古い判例が永久に対象外にならないようにする。

完了済みで固定資料との対応が確認できるページは再投入しない。本文・要旨が利用可能かは候補の詳細取得時に確認し、初期の詳細取得上限は新規・過去それぞれ8件/日とする。全件の詳細やPDFを毎回取得しない。候補の確認状況を保存して同じ不足資料だけを繰り返し確認しない。

## 2. 失敗・資料不足への対応

取得失敗、資料なし、LLM未完了、引用検査失敗を区別して保存する。一時的な失敗は1日後・3日後・7日後、その後は30日ごとに再確認する。試行数と次の確認日を持たせ、失敗する事件だけが処理枠を占有しないようにする。

本文未収録でも、判示事項・裁判要旨を根拠に要約できれば作成する。説明できない事案・理由等は既存の定型文で明示する。根拠本文も要旨もない場合は要約せず、資料待ちにする。PDF本文の後日追加は収集・配信側で行い、Wikiが使う配信済み資料との一致を維持する。

完了済みページの再要約は今回の日次過去枠に混ぜない。将来、本文追加で解説を改善する場合は、資料変更を検出する別の少件数枠として設計する。

## 3. 毎日の要約とリンク解析

`索引確認 → 新規/過去の候補選択 → 資料固定 → LLM解説 → finalize → 引用・形式検査 → Wiki保存` の順とする。

既存のLLM入力上限（判例と関連条文を合わせて最大36,000文字/件）と引用ルールを維持する。全ページにLLMによる要約・解説である旨、原文URL、収録範囲を表示する。検査失敗を含む未完成ページは完了数に含めない。引用文字列の一致と解説の意味的な正しさは区別し、初週は出力を人が抜き取り確認する。

リンク解析では、法令・条・項への言及、当時の条文候補、法令Wikiへの逆リンク、共通条文による関連判例を更新する。新しい判例が加わった時は既存判例側の関連一覧も再計算する。関連が少ないことだけを理由に再要約しない。先例関係や同じ結論であることを、共通条文から推定しない。

## 4. 公開まで確認する

Wikiブランチへの保存とサイト配信を別の進捗として記録する。現在の `Update law JSON` は更新判定がfalseだとWikiのexportも省略するため、法令更新がなくてもWikiの新しいコミットを次の定期配信で取り込めるようにする。

配信物に取り込んだWikiコミットSHA・export日時・判例件数を記録し、配信済みSHAとの差分を更新判定に含める。既存の12:30等の定期配信に合流し、Wiki生成のたびに全コーパスの強制再配信を追加起動しない。

配信後は公開JSONで件数と当日追加IDを照合する。失敗時はWiki側の完成ページを保持し、LLMを再実行せず次の配信で再試行する。生成から24時間以上公開されない場合は配信確認のチェックを失敗として記録する。将来のWiki単独配信は、法令・判例の配信物を欠落させずに更新できる方法として別途検討する。

## 5. 設定と日次レポート

設定として過去分の有効/無効、過去の件数上限、総件数上限、優先法令・分野を持つ。過去分0件で即停止できるようにする。既存CLIの引数の意味と手動ID指定は維持し、件数を意図せず増やさない。

GitHub Actionsの実行サマリーと公開進捗JSONに次を記録する。

- 新規/過去ごとの候補・試行・完了・保留・失敗件数。
- 累計Wiki作成数と公開済み件数、対象分野の作成数。
- 本文あり/要旨のみ/資料待ちの内訳、引用検査の結果。
- 関連法令数・関連判例の組数、Wikiと公開サイトそれぞれの更新日時。
- LLMが報告する使用量・費用と実行時間。契約上の請求額そのものとは区別する。

## 実装順と受け入れ条件

| 段階 | 作業 | 完了条件 |
|---|---|---|
| 1 | 過去候補の自動選択、種別ごとの件数枠、状態の保存と再試行 | 初回基準・試験10件を維持し、未処理だけを2件選べる。再実行しても重複せず、翌日は続きへ進む |
| 2 | 既存日次workflowへの接続、手動dry-runとサマリー | LLMなしで対象・選択理由・上限を確認できる。過去枠0件で既存動作へ戻る |
| 3 | Wiki更新を配信判定へ反映し、公開進捗を記録 | 法令更新0件でもWikiが次の配信へ入り、公開JSONの追加IDを検証できる |
| 4 | 過去2件/日で有効化して初週を確認 | 上限、重複抑止、失敗からの復帰、引用、関連リンク、公開反映を確認。増量は運用設定で判断 |

テストは、状態の旧形式互換、新規と過去の枠の分離、完了済み除外、日付不明、候補巡回、資料不足・一時障害、再試行の延期、未完成の再投入、法令更新なしのWiki配信を中心にする。引用・export・グラフは既存の回帰テストを再利用する。

最初の実装対象は段階1〜3。その後に既定の過去2件/日で定期処理を有効にし、初週の結果を見て優先分野と件数を調整する。
