# 判例を毎日要約してWikiへ追加する

2026-10-25更新。既存の `Update LLM wiki` に過去分の自動選択を組み込み、定期実行では **新規最大3件＋過去最大20件／日** を処理する。20件はLLMへ渡す上限であり、資料不足や生成・引用検査の結果によって完成数は減る。過去分は30日で最大600件、初週で最大140件となる。

索引44,980件、試験作成済み10件を引き継ぐ。既存10件は再要約しない。20件／日でも全体には約6年かかるため、行政・労務・生活保護のまとまりを優先して育てる。

## 実行と設定

毎日09:00 JSTの既存GitHub Actionsで実行する。開始時刻はGitHub Actionsの混雑によって遅れる場合がある。別の外部スケジューラーは不要。

| 設定 | 定期実行の既定値 | 内容 |
|---|---|---|
| `WIKI_MAX_HANREI` | 3 | 新規・手動指定判例の上限 |
| `WIKI_MAX_HANREI_BACKFILL` | 20 | 過去の自動追加上限。`0`で停止 |
| `WIKI_HANREI_PRIORITY_LAWS` | 生活保護法・行政事件訴訟法・労働基準法の法令ID | 優先する法令IDのカンマ区切り |

上記はRepository Variablesで変更できる。既存CLIの `--max-hanrei` の意味は維持し、過去分を独立した `--max-hanrei-backfill` にした。CLIおよび手動workflow実行では過去分は既定0件で、必要な場合だけ指定する。既存の `hanrei_case_ids` による最大10件の手動投入も維持する。

過去分を有効にした実行では、同日の選択数・詳細取得数をWikiブランチに保存する。同日に再実行しても日次枠を使い切った種別は追加しない。件数設定を増やした場合はその差分だけ追加できる。日付が変わると枠がリセットされる。

### LLMを呼ばずに候補を確認する

Actionsの `preview_hanrei=true` と `max_hanrei_backfill=20` を指定すると、候補ID・選択理由を実行サマリーに出す。状態保存・LLM・pushは行わない。CLIでも同じ確認ができる。

```sh
lawpub wiki-preview-hanrei \
  --base-url https://bokuweb.github.io/lawrenceanum \
  --wiki wiki --max-backfill 20
```

この表示は未処理索引からの新しい候補であり、資料の利用可否をまだ調べていない。再試行分・当日の残り枠・詳細取得結果を反映した実際のタスクは `wiki-plan` の `plan.json` で確認する。

## 候補選択と再試行

初回の索引基準 `seen` は「既知」を意味し、「要約済み」とは区別する。後から索引に現れたIDは新規、過去の自動追加は `backfill`、手動指定は `manual` として記録する。旧形式の保留は新規として読み込む。

過去候補は優先法令と全体の巡回枠を交互に選ぶ。優先法令内では既存Wikiと同じ条番号を扱う判例を先に選び、次にその他の関連判例を選ぶ。裁判日は和暦を正規化して新しい順、同日ならID順とする。日付不明も最後に残し、除外しない。全体の巡回位置は保存して翌日へ引き継ぐ。

新規と過去の詳細取得はそれぞれ1日最大80件（`max-probes`がそれより小さければその値）。全件の詳細やPDFを毎日取り直さない。過去の再試行は詳細取得枠の半分までとし、新しい候補にも枠を残す。

取得失敗・根拠となる本文や要旨の欠落・生成未完了を状態として保存する。自動取り込みでは1日後、3日後、7日後、その後は30日後に再試行する。LLMに渡した時点で次回日を記録するため、生成に失敗しても同日に繰り返さない。finalizeで完了が確認できた判例は保留から取り除く。生成または引用検査に通らず残った判例は `summary_incomplete` として再試行する。

## 要約・リンクと品質

既存の7節（要約・事案・争点・結論・判断と理由・射程と留意点・法令との関係）のLLM解説を使う。LLMによる要約・解説である旨、原文URL、本文・要旨の収録範囲を表示し、最大36,000文字の資料を固定して引用検査する。本文がなくても裁判所の判示事項・裁判要旨があれば使い、根拠がない節は資料不足と記載する。未完成のページは公開しない。

法令・条・項への言及と当時の条文候補を解析し、法令Wikiへの逆リンク、共通条文による関連判例、グラフも更新する。共通条文だけから先例関係や結論の一致を推定しない。完了済みの再要約はこの枠には混ぜない。

PDF本文の取得は既存の `update-corpus-data.yml`（最大200件／回）に任せ、配信された本文を再利用する。

## 公開の確認

完成ページは `wiki` ブランチに保存する。定期の `Update law JSON` が、配信済みWikiとブランチのSHAを比較し、法令更新が0件の日もWikiに差分があればキャッシュから配信物を構築する。Wiki生成のたびに追加の全コーパス配信を起動することはしない。

配信では最初に確認したWikiのSHAを固定し、export失敗時は公開を停止する。`wiki/index.json` に `source_commit`、export日時、判例進捗を記録し、`wiki/hanrei-progress.json` にも集計を出す。公開後にSHAと判例ID集合のダイジェストを照合し、件数だけの一致で成功としない。

日次Wiki処理は未配信を最初に検出した時刻を保存し、24時間以上継続した場合、生成済みページを保存したうえで実行を失敗として通知する。通信障害も確認失敗として記録する。未配信の完成ページを再要約せず、次の定期配信で再試行する。

Actionsのサマリーには当日の新規・過去の選択数、詳細取得数、保留の状態別件数を出す。既存のfinalize/checkレポートとLLMの実行時間・使用量も併用する。公開進捗は既知件数、完成数、新規・過去の保留数、状態別件数、当日の枠消費を集計し、約4.5万件の既知ID一覧そのものは公開進捗へ複製しない。

## 初週の確認

自動増量は行わない。初週は引用、資料不足の明示、要約の読みやすさ、関連リンク、処理時間・費用、公開反映を抜き取り確認する。引用文字列の一致は、解説の意味的な正しさを保証するものではない。
