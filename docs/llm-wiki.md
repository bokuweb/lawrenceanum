# LLM wiki (OKF)

国会会議録・審議会議事録を、法令 ID や法令名とのリンクを必須とせず、政策形成を会議から追える wiki に日次で積み上げる。
「いつ・どの会議で・誰が・どんな立場と理由で何を述べ、どうなったか」を、根拠・未確認範囲とともに残す。
形式は [Open Knowledge Format](https://agentic-ai.readthedocs.io/en/latest/Standards/open-knowledge-format/)
(Markdown + YAML frontmatter、必須は `type`)。

[public-corpus-roadmap.md](public-corpus-roadmap.md) の原則どおり、wiki は正規化コーパスの**下流の派生物**で、
正本は常に Pages の静的 JSON。wiki は消して作り直せる。

## 置き場所

- 本体: orphan ブランチ `wiki`（main と履歴を分け、日次コミットで main を汚さない）
- CI では `git worktree` で `wiki/` に展開する。作業領域 `.wiki-work/` とともに main では追跡しない。

```
wiki/
├── index.md                     # type: index（生成）
├── log.md                       # type: log（生成・日次追記）
├── laws/{law_id}.md             # type: law   — 経緯の要約 (LLM) + 時系列 (生成)
├── meetings/kokkai/{id}.md      # type: meeting — 要点 (LLM) + メタ (生成)
├── meetings/shingikai/{id}.md
├── bills/{回次}/{議案ID}.md     # type: bill   — 概要と経緯 (LLM: 提出理由・主な内容・附帯決議を引用付きで) + 審議経過・会派の賛否（生成）
├── pubcomments/{案件ID}.md      # type: pubcomment — 概要と結果 (LLM: 何の案か・主な意見と考え方・修正の有無) + 募集情報（生成）
├── kanpo/{日付}/{号-ページ-hash}.md # type: kanpo — 改正の内容 (LLM: 何をどう改め、いつ施行するか) + 掲載情報・官報の本文（生成）
├── committees/{会議体}.md       # type: committee — 開催回・扱った法令・発言者（生成）
├── parties/{会派}.md            # type: party   — 発言した人物・議案への賛否・提出した議案（生成）
├── people/{氏名}.md             # type: person — 全体像・発言と経緯 (LLM: 人物タスク) + 法令に言及した発言の一覧（生成）。国会は議事進行を除く発言者全員、
│                                #   審議会は官職者（例: 森光健康・生活衛生局長）。姓だけの委員は会議体ページに載せる
├── topics/{論点}.md             # type: topic  — 論点ごとのまとめ (LLM)
├── .lawpub/state.json           # 処理済み会議
├── .lawpub/intake.json          # 今回の候補範囲・未完了理由（export の index.json にも収録）
└── .lawpub/roster/{corpus}/{会議ID}.json  # 発言者名簿（生成）— 人物・会議体ページの元
```

### 会派（政党）ページ

`parties/{会派}.md` は、発言者名簿・会議ページが持つ発言者の会派と、議案ページの frontmatter
`votes`（院ごとの賛成・反対会派）・`proposer_groups`（提出会派）から作る。LLM は使わない。

- この会派として発言した人物（人物ページへのリンクと発言した会議数）
- 議案への賛否（日付・議案・院・賛否）と、提出した議案
- よく言及した法令（上位 30）

会派名は会議録・議案の**表記のまま**にする。院や会期で表記が変わる（「自由民主党・無所属の会」(衆)
と「自由民主党」(参) など）が、勝手に名寄せすると出典と食い違うので、名寄せは今はしない。
人物ページからは、最新の会派のページへリンクする。

### 人物・会議体ページはコーパスの全会議から作る

LLM が要点を書けるのは 1 日数件 (`WIKI_MAX_ITEMS`) で、対象も `lookback_days` の窓の中だけなので、
人物ページを会議ページの frontmatter からだけ作っていた頃は、窓からこぼれた会議の発言者が永久に載らなかった
（コーパスに 1,000 件以上の会議があるのに人物ページが 3 件、という状態になる）。

そこで発言者の抽出を LLM から切り離し、`wiki-plan` が**コーパスの全会議**について発言者名簿
`.lawpub/roster/{corpus}/{会議ID}.json`（会議の表記・原文 URL・言及した法令・発言者と会派）を作る。
`wiki-finalize` は会議ページと名簿を合わせて人物・会議体ページを作り、会議ページがまだ無い回は原文
（国会会議録・議事録）へ直接つなぐ。

- 日付の窓は無い。`lookback_days` は「LLM に要点を書かせる会議」の窓のままにする。
- 名簿は発言者ごとに、その会議で**法令に言及した発言の抜粋**（法令名の前後・原文のまま）と
  その発言の原文 URL も持つ。人物ページの「主な発言」に新しい順で最大 12 件を引用する（人物タスクで要約済みの会議は
  載せず、「発言と経緯」の要約から発言へリンクする。抜粋は要約前の会議のつなぎ）
  （原文をそのまま切り出すだけで LLM を通さないので、言い換え・捏造は起こらない）。
- 会議録は公開後に変わらないので、一度作った名簿は作り直さない（`ROSTER_VERSION` を上げたときだけ）。
- 国会は法令リンクの無い回の本体を取りに行かない（「法令に言及した発言者」の定義どおり）。
  リンクが無いことも名簿に残して、翌日以降に引き直さない。
- 審議会は件数が少なく資料だけでは中身がわからないので、議事録があれば必ず読む。
- 1 回の run で作る名簿は `WIKI_MAX_ROSTER`（既定 1200）件まで。LLM は使わず、1 会議あたり HTTP 数回。

### 人物ページの全体像と経緯（人物タスク）

会議タスクで人物ページの「発言と経緯」が埋まるのは、その日に LLM が要点を書いた会議（1 日数件）の発言者だけなので、
名簿から作った 1,000 件近い人物ページのほとんどは発言の一覧と引用しか無かった。そこで `wiki-plan` は会議とは別枠で、
1 日 `WIKI_MAX_PEOPLE`（既定 3）人ずつ、人物ごとのソースバンドルを作って LLM に渡す（`src/wiki/person.rs`）。

- **選び方**: 名簿の発言者（審議会の姓だけの委員を除く）のうち、ページの `llm_until`（要約済みの最後の会議の日付）より
  後の会議が残っている人を、残りの会議が多い順 → 発言した会議が多い順に選ぶ。よく発言する人から埋まり、
  新しい会議があればその分だけ書き足される。今日の会議タスクで経緯を書き足す人は、二重に書かないよう翌日に回す。
- **渡すもの**: 未要約の会議を古い順に最大 12 会議・24,000 字まで（同じ日の会議は分けない）。会議ごとに、その人の
  法令に言及した発言（最大 4 件）と、その直前の発言（答えた質問）・直後の発言（受けた答弁）。会議本体と法令リンクを
  取りに行くので、1 会議あたり HTTP 2 回。引用の照合用に会議本体を `.wiki-work/docs/` に残す。
- **発言へのリンク**: 「発言と経緯」の各項目は、発言 1 つの要約に `（[発言](発言の URL)）` と脚注を付ける。
  `wiki-check` は、LLM 区間にある発言単位の URL（`https://kokkai.ndl.go.jp/txt/{会議}/{番号}`）が、ページ内で検証済みの
  引用（脚注）の URL のどれかと一致することを確かめる（根拠の無いリンクを防ぐ）。
- **書くもの**: 「全体像」（論点ごとの主張・答弁のまとめ。法令ページの全体像と同じく、経緯の脚注を参照するだけ）と
  「発言と経緯」（会議ごとの日付見出しで古い順に追記）、`description`。
- **完了の判定**: LLM 区間が plan 時点から書き足され（hash が変わり）、引用が 1 つ以上あること。完了したら
  finalize がページの `llm_until` を進める。未完了なら翌日に同じ会議から渡し直す。渡せる抜粋が 1 つも無い
  （法令名が議事進行にしか出ない等）ときは LLM に渡さず `llm_until` だけ進める。

アプリへ書き出すとき（`wiki-export`）は、LLM 区間が空のままの節（見出しの直後が空の区間）を見出しごと落とす。
経緯がまだ無い人物ページや、全体像が未作成の法令ページに空の見出しだけが並ばないようにするため。

## アプリでの閲覧

グラフは 1,800 ページ・7,000 リンクを超えるので、全部を一度に力学配置すると毛玉になって読めない。
そのため SPA では、既定で**つながりの多い順に 250 件**だけを配置し（「表示範囲」で 100〜すべてに変えられる）、
ラベルは重なりを避けて上位だけ描く（ズームすると増える）。力は既定のままだと数百ノードで団子になるので、
反発と辺の長さを広げている（charge -320 / link distance 70）。
絞り込みの語はグラフにも効き、一致したページとその直接のつながりだけを描く。ページを開いたときは、
そのページと直接つながるぶんだけの図を「つながりを図で見る」から出せる。
一覧も一度に 300 件までにして、残りは絞り込みで探す。


法令ワークフロー (`update-law-data.yml`) が Pages へデプロイするとき、`wiki` ブランチを
`lawpub wiki-export` で SPA 用の JSON に変換して `public/wiki/` に同梱する。

```
public/wiki/index.json                 全ページの一覧 (type / title / description / date / tags)
public/wiki/graph.json                 ナレッジグラフ (ノード = ページ、エッジ = ページ間リンク)
public/wiki/report-manifest.json       資料用保存版 (ページ・主張・引用・参照関係と版)
public/wiki/page/{path}.json           frontmatter と本文 (Markdown)
public/wiki/enforcements/{law_id}.json 施行予定ごとの出典付き解説
```

SPA の `#/wiki` で、type 別に色分けしたナレッジグラフと一覧、各ページ（要点・出典の脚注・
つながっているページ）を閲覧できる。法令詳細画面には、wiki ページがある法令だけ「wiki」への導線が出る。
wiki の更新 (JST 09:00) は、次の法令ワークフローのデプロイ (JST 12:30 など) で反映される。

## 資料で使った根拠の保存と更新候補

`wiki-export` は配信用ページと同じ公開対象から `report-manifest.json` も生成する。
未完了の施行予定解説とハブページは含めず、要約待ちのページは `stub: true` として残す。
これは公開対象の Wiki の保存版であり、原文コーパス全体の保存・収集漏れの検査・原文の再照合は行わない。

`pages` は配信用ページと共通の ID（例 `meetings/kokkai/M1`）をキーとし、次を持つ。

- `revision`: `content` 全体の SHA-256。本文、frontmatter、抜粋範囲・留保、引用、確認状態、参照先を含む。
- `content`: 表示用 Markdown、frontmatter、`stub`、脚注 `citations`、本文の有向リンク `references`、構造化された `claims`。
- `content.claim_structure`: `unstructured`（旧形式など）、`invalid`（構造エラーあり）、`structured`。意味的な裏づけの検証状態とは別で、構造エラーは `claim_errors` に残す。
- `content.claims`: ページ ID・主張の文・種別・帰属先から計算した ID ごとの記録。`revision` は引用・発言者情報・レビュー状態を含む `records` の SHA-256。同じ主張が複数登録された場合も全記録を残す。

主張を書き換えたり帰属先を変えた場合は、旧主張の削除と新主張の追加になる。文面が同じまま根拠や確認状態が変わった場合は同じ ID の更新になる。
`generated_at` と JSON オブジェクトのキー順は版の判定に影響しない。`llm_supported` などのレビュー状態、`unsupported`、抜粋外の未確認範囲はそのまま保持し、検証済みへ昇格させない。

資料の作成時に保存版を **export 先の外** にコピーする（次の `wiki-export` は出力ディレクトリを作り直す）。
たとえば前回保存したものと今回のものを比較するには:

```sh
lawpub wiki-report-diff \
  --previous reports/2026-09/report-manifest.json \
  --current public/wiki/report-manifest.json \
  --out reports/2026-10/wiki-diff.json
```

結果の `changes` はページごとの `added` / `removed` / `updated`、新旧の版、主張ごとの変更種別を返す。
`review_candidates` は新旧の本文リンクを逆にたどった直接・間接の再確認候補で、値は変更のあった参照先の ID。
削除されたリンク先や新たに公開されたリンク先も対象になり、循環参照でも終了する。リンクは主張の支持関係ではなく、結論の変更や資料の自動書換えを指示するものではない。
入力の schema / scope と内容ハッシュを検査し、対応しない版や保存後に内容だけ変更されたファイルを拒否する。

PPTX など資料側での利用時は、スライド・図形の ID とともに **ページ ID・ページ revision・主張 ID・主張 revision** を保存する。
主張のない旧ページを使う場合もページ ID と revision を保存する。抜粋範囲などページ側だけの変更を拾うため、主張の版だけでは判定しない。
これにより前回使った本文・引用・留保と今回との差分を追える。PPTX の生成・図形への対応付け・顧客による編集との統合は、この CLI には含めない。

## 自治体の対応（例規）

`wiki-plan` は週 1 回、R2 に配信している自治体例規（約 300 自治体・22 万件）の題名を、wiki に法令ページがある法令の名前と
最長一致で照合し（4 文字未満の法令名は誤一致しやすいので除く）、法令ページに「自治体の対応（例規）」節（件数・自治体数・
最近の制定例）を載せる。LLM は使わない。ワークフローは Secret `R2_PUBLIC_URL` から配信元を組み立てる。

## 官報

法令ページの時系列に、その法令を改正する官報の項目と、その法令に基づく告示の改正を載せる。LLM は使わない。

- `kanpo-link`（法令ワークフロー）が、官報の目次の標題から改正対象の法令を引いて `kanpo/{date}/index.json` の
  `linked_laws` に入れる（`Xの一部を改正する政令` → X、`Xの一部を改正する法律の一部の施行期日を定める政令` → X）。
  e-Gov の改正履歴との突合は e-Gov への反映が数か月遅れて直近の官報に当たらないため、標題からも引く。
  告示は e-Gov に無いので、告示の改正は標題の先頭の根拠法令（`外国為替令第七条の規定に基づき、…`）を
  `basis_laws` に入れる。帰化・破産などの公告は改正の形の標題にならないので、どの法令にもつながらない。
  配信している日付の一覧は `kanpo/index.json`。
- `wiki-plan` が、wiki に法令ページがある法令について、その項目を frontmatter の `kanpo` にためる。
  デジタル官報の公開は約 90 日で配信側からも消えうるため、取り込んだ項目は wiki 側に残し続ける
  （対応付けの規則を変えたときは `KANPO_VERSION` を上げると引き直す）。官報だけでは法令ページを作らない。
- 改め文の本文が取れている項目は、官報ページ `kanpo/{date}/{slug}.md` を作る（wiki に法令ページがある法令に
  つながるものだけ）。ページには掲載情報と官報の本文（自動抽出）を載せ、`WIKI_MAX_KANPO`（既定 3）件ずつ
  LLM に「何をどう改め、いつ施行するか」を書かせ、法令ページの経緯にも追記させる。
- 官報の引用 `[kanpo:{date}/{slug}](PDF) 「…」` は、配信側ではなく**官報ページに保存した本文**と照合する。
  デジタル官報は約 90 日で消え、パーサの改善で抽出結果も変わるため。要約済みのページは本文を固定する。
- `wiki-finalize` が時系列表に描く。e-Gov に反映済みの公布の行には「官報」へのリンクを付け、
  まだ反映されていない改正と告示の改正は「官報」の行として足す。官報ページがあればそちらを指し、
  LLM が書いた 1 行を添える。
### 施行予定ごとの解説

`wiki-plan --max-enforcements 5` は会議・議案とは別枠で、将来の施行予定を近い順に選ぶ。
`enforcements/{law_id}/{explanation_id}.md` に「変更内容」「経緯」「根拠」を生成し、
施行予定一覧（展開時に取得）と法令詳細（直近分を展開）に表示する。
ID は法令・改正イベント・revision・施行日の組み合わせから作り、段階施行を区別する。

原文は対象イベントの官報、対象 revision と施行日が一致する条文差分、対象改正を特定できる
パブコメから集める。パブコメは改正命令名の完全一致（末尾の案表記を除く）と公布前180日以内の
公示・受付終了日を条件とし、同名の別改正がある場合は使わない。法令名だけの一致では採用しない。
官報・パブコメは改正全体の資料であることを LLM に伝え、その施行日に適用される変更を
特定できなければ記述しない。経緯や根拠を確認できない節には「確認できる資料がありません。」と表示する。
原文が一つもない予定には推測の解説を生成せず、画面では未生成と表示する。

引用は `[enforcement:{law_id}/{explanation_id}#{source_id}](原本URL) 「原文」` の脚注形式。
既存の `wiki-check` が原文・URLを照合し、各節の出典または確認不能の明示と、対象イベントの一致も検証する。
入力資料の指紋が変わったページは再生成する。`wiki-export` は配信するコーパスと指紋が一致する
完了ページだけを書き出すため、資料の更新後に古い解説を表示しない。

Actions の `max_enforcements` / リポジトリ変数 `WIKI_MAX_ENFORCEMENTS`（既定5、0で無効）で
生成数を制限できる。ソース候補の探索は `--max-probes` 件まで、LLM 入力は1予定あたり最大36,000字。
既存の Claude 認証・引用検証・修正・wiki ブランチへの保存・次回 Pages 配信をそのまま利用する。

## 日次の流れ (`.github/workflows/update-wiki.yml`, JST 09:00)

| 段階 | 実行者 | 内容 |
|---|---|---|
| `lawpub wiki-plan` | 決定的 | 未処理の会議を新しい順に見て、法令リンクの有無によらず最大 `WIKI_MAX_ITEMS` 件選ぶ。法令言及と前後の文脈、または会議全体のダイジェストを上限付きで抜粋したソースバンドルと、ページの雛形を作る。あわせて議案（件名から対象法令を決める）と法令の改正履歴（直近 10 年の公布・施行）と官報の項目、コーパス全会議の発言者名簿を取り込む |
| Claude Code | LLM | `.github/wiki-agent.md` に従い、抜粋だけを根拠に、会議の要点と、法令・会議体・人物・論点ページの「経緯」（古い順の日付見出し。誰が・何について・どんな理由で・何を述べ・どうなったか）を引用付きで書き足す。使えるツールは wiki/ の Read/Edit/Write のみ（Bash・ネットワークは無し）。タスクは `wiki-plan` が 4 件ずつのチャンク（`.wiki-work/chunks/NNN.md`）に分け、チャンクごとに新しい Claude Code（CLI）を呼ぶ（一度に何十件も渡すと途中で切り上げてしまうため） |
| `lawpub wiki-finalize` | 決定的 | 法令ページの時系列表（会議・議案の経過・公布/施行・官報を 1 本に。改正法は法律番号で議案ページにつなぐ）、人物・会議体ページ（会議ページ＋発言者名簿）、index、log を再生成する。未完了の会議は雛形を消して翌日に回す |
| `lawpub wiki-check` | 決定的 | OKF frontmatter・相対リンク・引用を検証する。失敗したら LLM に 1 回だけ修正させ、それでも駄目なら push しない |

### 調査用の全体像と更新の完了判定

法令の全体像は「背景・経緯」「争点」「政府見解」「決定・結果」「未決事項」「確認範囲」の6項目で書く。
政府側の答弁には発言者・役職・日付を付け、議員や参考人の意見と区別する。資料がない項目は
「収録資料からは確認できない」と明示し、附帯決議の要請を政府の実施約束と扱わない。
根拠は経緯の脚注、または議案等の機械データへのリンクでたどれるようにする。
これは LLM への編集指示であり、各主張の意味上の裏付けまで機械で保証するものではない。
`NARRATIVE_VERSION = 3` により、旧形式の会議も通常の件数上限内で順次再投入し、関連法令の全体像を更新する。

国会の抜粋には、法令に触れた発言の前後で最初に現れる実質的な発言を補う（片側4発言まで探索、
追加分は会議あたり3,000字まで）。委員長の指名を挟む答弁や、法令名を繰り返さない質問も材料にできる。
`context_for` で起点の発言を示すが、近接だけで応答関係を確定せず、文脈から法令との直接リンクを追加しない。
長い発言は冒頭・最初の留保候補（ただし・一方・反対等）・末尾を優先する。条件をすべて拾う保証はない。
`source_scope` に全発言数・収録数・部分収録 ID・未収録 ID を残し、画面でも公開する。
抜粋は網羅的ではないので、確認した資料の範囲を全体像にも示す。

`plan.json`（schema version 2）の `before` は全タスクの主ページの LLM 区間の hash を保持する。
`wiki-finalize` は引用と description に加えて、この区間が plan 時点から変わったことを確認してから、
会議の処理済み状態、議案の `llm_latest_date`、パブコメの `llm_result_date` 等を進める。
機械生成の表や description だけの変更では完了にしない。更新されなかった既存ページは残して再試行する。
`before` がない旧 plan は互換性のため従来の判定になる。この判定は編集の実施を確認するもので、要約の品質評価は別途必要。

### 引用の検証

LLM の記述には必ず脚注で根拠を付ける。

```
[^1]: [kokkai:122105261X01720260727_044](https://kokkai.ndl.go.jp/txt/122105261X01720260727/44) 「今直ちに新たな有識者会議を設置する考えはございません」
```

`wiki-check` は、発言 ID が実在すること、URL がその発言のものであること、「」内が発言本文の
連続した一節であること（空白は無視）を照合する。言い換えや捏造された引用は push 前に落ちる。
新形式の会議は、審議会でも同じ発言単位で照合する。旧ページの発言番号ずれを許す全文照合は主張の帰属に使わない。

### 主張ごとの根拠と意味上の支持

会議ページの `claims` は本文の主張 `text`、種類 `kind`、帰属発言 `attribution`、脚注ラベル `evidence`、
`review_status` と理由 `review_note` を持つ。`wiki-finalize` は対応のない要約を完了にせず、`wiki-check` も構造を検査する。
`evidence_sources` は機械が発言 ID・URL・日付・発言者・会派/所属・役職・立場を保存し、check で原資料の発言者等と照合する。
処理中の会議は日付・取得範囲・出典情報も生成時のソースバンドルと照合し、LLM による書き換えを拒否する。
政府側は明示された官職等、有識者・業界側は明示された所属・役職に限って分類する。姓と「委員」「参考人」だけでは推定しない。
`government_view` は政府側の根拠発言に限定するが、政府側が述べたことと確定方針は区別する。

判定は生成 LLM の自己点検で、独立した審査ではない。状態は `unreviewed` / `needs_review` / `unsupported` /
`indeterminate` / `llm_supported`。未審査・要確認・支持しない・判定不能も保存して表示する。
`llm_supported` は暫定判定であり、意味の正しさを保証しない。「検証済み」の状態は設けない。
本文の全主張が登録されたかは機械では保証せず、未登録部分は未確認と表示する。
export は `claim_assessments` に根拠情報と原文引用を結び、UI から主張ごとの話者・日付・原文をたどれる。
旧ページは情報未整備と表示する。関連法令・人物等への転記も、元の主張より強い断定にしない。

### 取り込み範囲と未完了

`.lawpub/intake.json` の対象は日付窓内の未処理・処理済み会議と旧形式ページ。候補ごとに `budget_pending`（上限）、
`source_unavailable`（資料取得待ち）、`no_substantive_text`（実質的本文なし）、`planned`（要約待ち）を記録する。
finalize 後は `completed` または `summary_pending` に更新する。Actions Summary と wiki トップで範囲と未完了を表示する。
処理済み会議の再取得で資料の版が同じなら `source_unchanged` とし、未完了件数から除く。
旧 `no_link` / `formal_only` / `no_excerpt` は完了と扱わず、日付窓内で再試行する。
窓外・未収集資料は集計外であり、新しい順の選定が続くと古い候補が窓外になる可能性もある。網羅性を意味しない。

### 原資料の訂正と要約の版

会議の `source_fingerprint` は、抜粋外を含む全引用単位の本文・発言 ID・URL・話者・所属・役職と、
日付・会議名・議題・法令対応の SHA-256。取得時刻など収集だけのメタ情報は含めない。
`llm_source_fingerprint` は最後に要約を完了した資料の版で、finalize だけが更新する。
どちらもソースバンドルと照合し、LLM が完了マーカーを先に進めても受理しない。

未処理を先にし、処理済み会議は `.lawpub/state.json` の取得試行順で巡回する。
取得失敗も順序を進める。原資料の変更または版の記録が無い場合は通常の会議タスクとして再投入し、
取得は既存の `max_probes`、再要約は `max_items` の範囲に収める。変更が無ければ会議ページを書き直さない。
日付窓外の現行形式ページは再取得しない。窓内でも未処理が上限を使い切れば再確認は繰り越しとなり、
原サイトに訂正が出てからコーパスに反映されるまでの遅延もある。

再要約が完了するまで旧本文は保存し、UI で更新未完了と表示する。`claim_assessments` と資料用 manifest では
旧主張の判定を `indeterminate` に戻し、旧引用と更新後の話者情報を組み合わせた根拠一覧は出さない。
引用そのものが訂正されて原文と一致しなくなった場合は check が失敗し、修正が済むまで公開を止める。
人物・会議体・法令の機械生成時系列にも「原資料更新・要再確認」を付ける。
関連ページの LLM 本文は自動で修正せず、manifest の差分・逆参照による再確認候補を使う。
版の記録がない旧ページには追随状況未確認と表示する。同じ版に対応していても、意味上の支持や最新性の保証にはならない。

### コスト上限

- 1 回あたりの会議数: `WIKI_MAX_ITEMS`（既定 5）、議案数: `WIKI_MAX_BILLS`（既定 5。経過が進んだ議案も再要約）、パブコメ数: `WIKI_MAX_PUBCOMMENTS`（既定 3。結果公示済みの案件）、官報の項目数: `WIKI_MAX_KANPO`（既定 3。1 項目あたり本文 12,000 字まで）。1 会議ごとに会議・法令・会議体・人物ページへ経緯を追記する。法令リンクの無い会議も同じ上限内で LLM に渡す。
- 法令言及は最大12発言・8,000字に前後の文脈3,000字までを追加する。法令のない会議や審議会のダイジェストは12,000字まで。会議全文は渡さない。
- 未処理の残りは翌日以降に新しい順で消化する（`lookback_days` 既定 45 日）。
- 発言者名簿はこの上限の外。LLM を呼ばないので、コーパスの全会議が対象。

## セットアップ

1. Claude の認証を Secrets に登録する。個人の Pro / Max プランで動かす場合（推奨）:

   ```bash
   claude setup-token                          # ブラウザでログインし、1 年有効の OAuth トークンを発行
   gh secret set CLAUDE_CODE_OAUTH_TOKEN       # 表示されたトークンを貼り付ける
   ```

   利用量はそのプランの上限から消費される。従量課金にしたい場合は代わりに `ANTHROPIC_API_KEY` を登録する。
2. 任意で Variables に `WIKI_MODEL`（既定 `claude-sonnet-5-5`）と `WIKI_MAX_ITEMS` を設定する。
3. Actions → "Update LLM wiki" を手動実行する。初回は `wiki` ブランチが orphan として作成される。
   - 試運転は `push_mode: pr` にすると、`wiki` 宛ての PR で差分を確認できる（2 回目以降。PR を
     マージするまで state が進まないので、日次運用は `direct` にする）。
   - PR モードを使う場合は、Settings → Actions → "Allow GitHub Actions to create and approve pull requests" を有効にする。

## ローカルで試す

```bash
cargo build --release -p lawpub-cli
git init wiki   # --changed で変更ページを判定するため
./target/release/lawpub wiki-plan --max-items 3
claude -p "\`.github/wiki-agent.md\` の指示に従い、\`.wiki-work/plan.md\` の全タスクについて wiki を更新してください。" \
  --allowedTools "Read,Glob,Grep,Edit(wiki/**),Write(wiki/**)" --disallowedTools "Bash,WebFetch,WebSearch"
./target/release/lawpub wiki-finalize
./target/release/lawpub wiki-check --changed
```

`--base-url` にローカルの `public/` を渡せば、Pages ではなく手元のビルド結果から作れる。
